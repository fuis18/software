An attacker no longer needs to break the firewall: it's enough for a component of the running software to be compromised. Supply chain security protects that flow — from dependency to deployed image.

## SBOM (Software Bill of Materials)

The SBOM is the **list of all components** in the software: every dependency, library, and their exact version. It's the inventory that lets you know what each artifact contains.

| Tool         | Role                             |
| ------------ | -------------------------------- |
| **Syft**     | Generates SBOM from images and codebases |
| **CycloneDX** | Standard SBOM format           |

- **Syft** generates the inventory: from a container image or a code directory, it lists every package and its version.
- **CycloneDX** is the format: a standard SBOM representation that lets different tools produce and consume the same inventory.
- **Why it matters** — without an SBOM, you can't answer "does this vulnerability affect us?" when a CVE is published: with the SBOM, the analysis is a search through the inventory.

## Image Scanning

The SBOM says what's there; scanning says **what of that is vulnerable**.

| Tool        | What it does                                       |
| ----------- | -------------------------------------------------- |
| **Trivy**   | Vulnerability scanning on images and filesystems   |
| **Grype**   | Vulnerability scanning on the SBOM (from Syft)     |

- **Trivy** — the standard: scans the image against known vulnerability databases and reports CVEs by layer and package.
- **Grype** — works on the inventory generated by Syft: same goal, going from the component list to vulnerabilities.
- **When** — scan before pushing the image to the registry and throughout its lifecycle, since new vulnerabilities appear over time. The image workflow details are in [ops-containers](../../ops/ops-containers/).

## Artifact Signing

Scanning doesn't prove authenticity: signing verifies that the artifact is exactly what a legitimate author built — not one impersonated or modified along the way.

| Tool        | What it does                                       |
| ----------- | -------------------------------------------------- |
| **Cosign**  | Signs and verifies container images                |
| **Sigstore** | Open source software signing ecosystem           |

- **Cosign** signs images with keys or with the **Sigstore** service, and lets you verify that signature before deploying — the same "signed images" idea that appears in the security chain of [ops-containers](../../ops/ops-containers/).
- **Sigstore** solves key management: signing, verification, and short-lived certificate transparency, without having to operate your own PKI infrastructure.

## Secure Builds (SLSA)

SLSA (Supply-chain Levels for Software Artifacts) is the **framework for reproducible and verifiable builds**: levels that define how trustworthy the chain that produced an artifact is.

| Level | What it guarantees                                        |
| ----- | --------------------------------------------------------- |
| **L1** | The build is documented                                  |
| **L2** | The build is reproducible and versioned                   |
| **L3** | The build is hermetic and tamper-resistant                |
| **L4** | The build is end-to-end auditable and authorized          |

- **The progression** — each level adds guarantees about how the artifact was built: who built it, with what source, and that no external party could alter it in the process.
- **In practice** — SLSA elevates the reproducible build principles of [ops-ci](../../ops/ops-ci/) to a measurable standard: the goal is that the deployed artifact can only come from a verified build.

> The full chain ensures end-to-end integrity: SBOM (what's there) → scanning (what's vulnerable) → signing (what's authentic) → verified build (how it was built). It's the layer that turns the [ops-ci](../../ops/ops-ci/) pipeline into a trustworthy pipeline.
